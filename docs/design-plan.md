# Job Search Agent: Implementation Plan for Cursor

## 0. How to use this plan (read first, Cursor)

This is a standalone project built on the **OpenAI Agents SDK** with a local browser GUI. Follow these rules throughout:

1. **Study the project before writing anything.** Read the agent definition, tool definitions, run loop, storage, and GUI code. Reuse the project's patterns, file layout, naming, and config handling.
2. **Work in phases.** Complete one phase, run it, show me what changed, and **stop and wait for my approval** before starting the next.
3. **Do not invent SDK APIs.** Check the installed version of the Agents SDK (and the GUI library) and use only features that exist in that version. If something in this plan is not supported, tell me and propose an alternative.
4. **Keep existing project behavior working** unless I explicitly say to remove it.
5. **Secrets stay in `.env`.** Never hard-code API keys.
6. **Keep it simple.** Local JSON/Markdown files, no database server, no vector store, no web scraping.
7. **Deterministic code for deterministic work.** IDs, dates, file writes, status changes, and keyword search are plain Python functions. The LLM is used only for extraction, judgment, and writing.
8. **All codes for this project will be housed under project/ folder.**

## 1. Project goal and course context

A personal job-search assistant that:

- saves job postings (pasted from LinkedIn/Indeed/etc. or loaded from files) into a posting database,
- stores my resume and extra experience as an experience database,
- analyzes my fit for a posting (fits, gaps, what to add to my resume),
- tracks which jobs I have applied to,
- searches past postings and flags possible duplicates.

This is a course project (CS619). The grade depends mainly on **three human-centered design ideas**, so these must be clearly visible in the GUI, not hidden in the backend:

| Idea | Course week | Where it appears |
|---|---|---|
| **A. Verifying AI output** | Week 2 | Every fit claim in the analysis cites the posting requirement ID and the experience entry ID it is based on; a separate check flags unsupported or stretched claims; the GUI lets me click a claim to see both pieces of evidence. |
| **B. Agent memory with user approval** | Week 4 | The agent proposes new experience entries and preference updates; I approve, edit, or reject before anything is saved. |
| **C. Human oversight at the right moment** | Week 4 | The agent asks me to confirm extracted postings, clarify vague experience, and confirm duplicate matches, and shows exactly what will be saved at the moment of approval. |

## 2. Data layout

All data lives under a `data/` folder (add it to `.gitignore`, since it contains my personal information).

```
data/
  postings/
    JOB-0001.json          structured record
    raw/JOB-0001.txt       exact text I pasted (kept as evidence)
  experience/
    experience.json        list of experience entries
    resume_source/         original resume file(s)
  tracking/
    log.jsonl              append-only event log
  config/
    analysis_instructions.md   my instructions for how analysis output should look
  analyses/
    JOB-0001_<timestamp>.json  saved analysis results
  interaction_log.jsonl    record of my approvals/rejections/edits (for evaluation)
```

### 2.1 Posting record (`JOB-xxxx.json`)

Fields:

- `id`: sequential, `JOB-0001` format, generated by code (never by the LLM)
- `title`, `company`, `department` (nullable), `location`, `employment_type` (nullable)
- `source`: e.g. `linkedin`, `indeed`, `company site`, `file`, `other`
- `source_url` (nullable)
- `date_added`: today's date, set by code
- `date_posted`: absolute date if known, otherwise an estimate
- `date_posted_is_estimate`: true/false (for text like "2 weeks ago", convert relative to `date_added` and mark as estimate)
- `requirements`: list of objects `{ "id": "REQ-1", "text": ..., "type": "required" | "preferred" }`
- `responsibilities`: list of strings
- `salary` (nullable, only if stated)
- `status`: one of `saved`, `applied`, `interviewing`, `offer`, `rejected`, `withdrawn`. **This is the single source of truth for status.**
- `notes` (nullable)

Extraction must drop page noise (navigation, "similar jobs", "people also viewed", ads) and must **not** store names or profile details of recruiters or other people.

### 2.2 Experience entry (in `experience.json`)

Fields:

- `id`: `EXP-0001` format, generated by code
- `source`: `resume` (parsed from my resume) or `user-added` (told to the agent later)
- `on_resume`: true/false
- `category`: `work`, `project`, `education`, `skill`, `leadership`, `award`, `other`
- `text`: one atomic, factual statement in my own terms
- `skills`: list of keywords
- `organization` and `dates` (nullable)
- `date_added`

Rule: one entry = one verifiable fact. Do not merge several achievements into one entry.

### 2.3 Tracking log (`log.jsonl`)

Append-only, one JSON object per line: `{ "timestamp", "job_id", "event", "details" }`. Events include `added`, `status_changed`, `note`. Changing status updates the posting's `status` field **and** appends to this log in the same operation.

### 2.4 Analysis instructions (`analysis_instructions.md`)

A plain Markdown file I edit by hand describing sections, tone, and length of analysis output. Create a sensible default version. The analysis tool must read it every time.

## 3. Tools

Implement these as Agents SDK function tools, following the project conventions. Clear docstrings matter, because they become the tool descriptions the model sees.

### Read tools (no approval)
- `list_postings(status=None)`: short summary per posting
- `read_posting(job_id)`
- `search_postings(company=None, department=None, title_keywords=None, status=None)`: case-insensitive keyword matching; return matches with the fields that matched
- `read_experience(category=None, source=None)`
- `search_experience(keywords)`
- `read_tracking_log(job_id=None)`

### Write tools (approval required, see Section 4)
- `add_posting(raw_text, source, source_url=None)`: LLM extracts a structured record; the code assigns ID and dates; the record is **shown to me for confirmation before saving**; the raw text is saved alongside
- `import_resume(upload_id)`: parse a resume selected with the browser upload control (support PDF, DOCX, and plain text) into atomic entries marked `source: resume`; the agent has no path-reading tool; show all proposed entries for review before saving
- `propose_experience(text, ...)`: propose a new `user-added` entry from details I give in chat; saved only after approval
- `update_experience(exp_id, ...)`: edit an existing entry; approval required
- `update_status(job_id, new_status, note=None)`: updates status and the log

### Analysis and checking
- `analyze_fit(job_id)`: see Section 5
- `check_claims(analysis_id)`: see Section 5
- `find_duplicates(job_id or draft posting)`: see Section 6

### Human interaction
- `ask_user(question, reason)`: for clarifying questions; the reason is shown to me

## 4. Human oversight and approval policy (Idea C)

Use the Agents SDK's built-in human-approval mechanism (tools marked as needing approval, with the run pausing on interruptions and resuming from saved run state). Check exactly how the installed SDK version supports this before implementing.

| Action | Policy |
|---|---|
| Reading, searching, analyzing | Automatic |
| Saving a new posting | Approval: show the extracted record, with requirements listed, next to the raw text |
| Saving resume entries | Approval: show all proposed entries; allow editing or removing individual entries before saving |
| Saving or editing experience | Approval: show the exact entry text as it will be stored |
| Changing application status | Automatic when I state it clearly ("I applied to JOB-0003"); ask if the job is ambiguous |
| Treating a posting as a duplicate | Never automatic; I decide |
| Anything that sends data outside my machine (email, submitting applications) | **Not implemented** in this project |

The approval card in the GUI must show **the exact content being saved**, not a summary, and offer **Approve**, **Edit**, and **Reject**. An edit must save my edited version.

**Clarification policy (put into the agent instructions):**
- Ask when my experience description is vague about my role or impact (e.g. "helped with" vs "led", or no scale/outcome given), and give me concrete options.
- Ask when a posting's company or title is unclear after extraction.
- Do not ask about minor details that can be fixed later; use a sensible default and say so.
- Ask at most one or two questions at a time.

## 5. Analysis with verification (Idea A)

### 5.1 `analyze_fit(job_id)`

Inputs: the posting's requirements, the full experience database, and `analysis_instructions.md`.

Output: a structured result (save it in `data/analyses/`) containing, for each requirement:
- `requirement_id` and requirement text
- `verdict`: `strong match`, `partial match`, `gap`
- `evidence`: list of `EXP-xxxx` IDs supporting the verdict (empty for gaps)
- `explanation`: one or two sentences

Plus these sections:
- **What fits:** strong and partial matches
- **What doesn't fit:** gaps, separated into required vs preferred
- **Add to your resume:** only `user-added` entries with `on_resume: false` that match requirements, each citing its EXP ID
- **Questions for you:** gaps where I might have relevant experience that is not in the database, phrased as questions (e.g. "Have you used Tableau?")

Hard rules (put these in the prompt **and** enforce in code):
- Every match must cite at least one existing EXP ID and one existing REQ ID. Code validates that cited IDs exist; if not, mark that claim as invalid.
- Never suggest adding experience that is not in the database. Missing experience becomes a question, not a suggestion.
- Then format the result for display according to `analysis_instructions.md`.

### 5.2 `check_claims(analysis_id)`

A **separate** LLM call, with its own instructions, that re-reads each (requirement text, cited experience text) pair and rates the support: `supported`, `stretched` (the evidence is related but weaker than claimed), or `unsupported`, with a one-line reason. Run it automatically after every analysis.

### 5.3 GUI for verification
- Each fit claim is displayed with a small badge (supported / stretched / unsupported).
- Clicking a claim shows the requirement text (with the matching line highlighted in the raw posting if possible) and the cited experience entries side by side.
- Order claims so **stretched and unsupported ones appear first**, since those are the ones worth my attention.
- I can mark any claim as "I agree" or "I disagree", and this is logged (Section 8).

## 6. Search and duplicate detection

`find_duplicates` runs automatically when a new posting is being added, and on request.

1. **Candidate search (code):** normalize company names (lowercase; strip suffixes like "Pte Ltd", "Ltd", "Inc", "Bank"; strip punctuation) and title words, then find postings that share the company plus any overlapping title keywords.
2. **Judgment (LLM):** for each candidate, return `likely same posting`, `same company, different role`, or `unrelated`, with a one-line reason (e.g. "same team; title differs only by 'Senior'").
3. **Decision (me):** show the candidates with reasons. I choose whether to save as new, skip, or link to the existing posting. Never merge or delete records automatically.

When I ask "Have I applied to X before?", use `search_postings` and report matches with their statuses and dates from the tracking log. If nothing matches, say so plainly, and mention near-misses if any.

## 7. Memory with user approval (Idea B)

- When I mention experience in conversation (e.g. "I also led my hackathon team last year"), the agent should **propose** saving it via `propose_experience`. It must not save it silently.
- The proposal shows the exact entry text. The agent must not upgrade my wording ("participated" must not become "led").
- If I correct the agent's analysis style repeatedly (e.g. "shorter", "put gaps first"), the agent may propose an edit to `analysis_instructions.md`. This also requires approval, and the GUI shows the change as a before/after diff.
- Add a GUI view listing all experience entries with filters by `source` and `on_resume`, where I can edit or delete entries directly.

## 8. Interaction logging (for the evaluation)

Append every human decision to `data/interaction_log.jsonl`: `{ timestamp, event_type, item_type, item_id, decision (approve/edit/reject/agree/disagree), time_to_decision_seconds, before, after }`.

This supports my evaluation (e.g. how often I catch stretched claims vs accept them, and how often extractions needed edits). Also add a small script to summarize this log into counts.

## 9. Agent instructions (system prompt contents)

Write the agent's instructions to cover:
- its role as a job-search assistant working only from the saved databases;
- when to use each tool;
- the citation rules and the rule against inventing experience;
- the clarification policy (Section 4);
- the memory proposal rules (Section 7);
- the requirement to refer to postings by ID and title, e.g. "JOB-0003 (Data Analyst, DBS)";
- a friendly, concise tone.

Keep the instructions in a separate file so I can edit them.

## 10. GUI requirements

Build on the project's local browser GUI. At minimum:

1. **Chat panel:** normal conversation with the agent.
2. **Approval cards:** rendered inline when a write tool needs approval; Approve / Edit / Reject.
3. **Analysis view:** requirements with verdict badges and the evidence panel (Section 5.3).
4. **Postings view:** table of postings with ID, title, company, date added, status; click to open.
5. **Experience view:** Section 7.

If the GUI framework cannot support a feature (e.g. the side-by-side evidence panel), tell me and propose the simplest workable alternative before building anything elaborate.

## 11. Phases and acceptance checks

Stop after each phase for my review.

**Phase 0: Explore.** Summarize the repo structure, the SDK version, how tools, the run loop, and the GUI work, and how human approval is supported. Point out anything in this plan that conflicts with the codebase. *No code changes.*

**Phase 1: Storage layer.** Folders, ID generation, read/write helpers, status update plus log, and unit tests. *Check:* tests pass; IDs never collide; a status change updates both the record and the log.

**Phase 2: Add posting.** Extraction, confirmation card, save. *Check:* pasting a messy LinkedIn page yields a clean record with REQ IDs; nothing is saved without approval; recruiter names are not stored.

**Phase 3: Resume import and user-added experience.** *Check:* a resume becomes atomic EXP entries after review; a chat mention produces a proposal card; rejected proposals are not saved; wording is not inflated.

**Phase 4: Analysis and claim checking.** *Check:* every match cites valid IDs; invalid IDs are flagged; "Add to your resume" includes only entries not on the resume; missing experience appears as questions; the output follows `analysis_instructions.md`.

**Phase 5: Verification GUI.** Badges, evidence panel, agree/disagree logging.

**Phase 6: Tracking, search, duplicates.** *Check:* "I applied to JOB-0002" updates status; "Have I applied to DBS before?" finds records despite company-name variants; duplicates are never merged automatically.

**Phase 7: Interaction logging and summary script.**

**Phase 8: Polish.** Error handling, a README section describing the three design ideas, and a small set of sample postings and a sample resume with fake data for demos and testing.

## 12. Out of scope

- Automatic scraping of LinkedIn, Indeed, or any job site
- Submitting applications or sending emails
- Generating full tailored resumes or cover letters (possible later extension)
- Multi-user support or authentication
